# Progress: speaker-page

## Original Goal

Implement speaker page: 1. Display all segments for the given speaker across all sessions, grouped with each of their generated clips and transcription, preparing the entire collection for proper dataset export

The current implementation in workers/clip-worker.ts is old code and should not be taken into consideration. We shall implement a new approach from scratch that is better suited for this new flow.

Transcriptions should not be its own table but rather a new column in the segments table.

Segments have a speaker id which can be used to directly query for all to a given speaker

The speaker page UI should be as follows:
- Header spanning entire width of the screen with back button + speaker name on the left-hand side and "Export" button on the right-hand side
- Main section consisting of:
  - List area (left):
    - List header containing List filters
    - Core unit list, where each item consists of: segment and generated clip side by side, transcription below.
  - Sidebar (right):
    - Section with speaker stats on the top half (Total segments, Avg MOS score, MOS score distribution, segment length distribuition)
    - Section with processing actions on the bottom half (denoise, remove overlap, transcribe, etc...)


Export functionality should allow user to configure how they wish to export the clips (audio format, sample-rate, etc...) We store them as FLAC for best lossless storage on the cloud. Show presets (e.g. LJSpeech) for better UX.

Key Design Decisions:
- Transcriptions come from diarization service, with per-segment transcription trigger capability
- Clips stored as FLAC, converted on export
- Quality scoring for review purposes only
- Filter criteria: Duration, quality score, has transcription
- Access to all sessions
- No "Generate Clips" action - clips generated automatically on processing
- One clip per segment (clip history out of scope)
- Processing operations are additive; delete clip to restart
- All processing goes through queue (inherently batch)
- Processing Queue summary in sidebar for visibility
- Segments use media-proxy endpoint for audio data
- Lazy loading for both segments and clips audio (show spinner on download)
- Filters in List Header, not sidebar
- Export zip streamed directly (not stored in R2)
- No cursor pagination needed for now

## Learnings

- LJSpeech format: 22050Hz, 16-bit mono WAV, pipe-delimited metadata.csv
- Pyannote API does NOT provide transcription - only speaker diarization. Need separate service (OpenAI Whisper recommended)
- Project uses Biome for linting (not ESLint), type checking via MCP getDiagnostics tool
- Existing media-proxy already supports time-slice streaming via startMs/endMs params
- BullMQ queue infrastructure exists with waveform worker pattern to follow
- archiver library can stream ZIP directly to HTTP response without file storage
- Clips table should have 1:1 relationship with segments (unique constraint on segmentId)
- FFmpeg already available via fluent-ffmpeg package and stream-audio.ts patterns
- Legend-State used for client state management throughout clipping feature
- Radix UI + TailwindCSS for component library patterns
- Requirements: 10 user stories defined with 54 acceptance criteria
- Requirements: 20 functional requirements prioritized (P0-P2)
- Requirements: Service interfaces needed for TranscriptionService, DenoiseService, OverlapRemovalService, ClipGenerationService
- Requirements: All services follow Effect.js Context.Tag pattern per existing codebase
- Requirements: Transcription should be column on segments table, not separate table (simplifies queries)
- Requirements: MOS score is manual annotation only, not automated scoring
- Requirements: Export must respect filter selection (filtered export is default behavior)
- Requirements: Risk identified around large segment counts - may need virtual scrolling
- Design: Architecture uses three layers - Client (Legend-State store), API (tRPC + export endpoint), Services (Effect.js Context.Tag)

- Design: Client-side filtering chosen over server-side since all segments fetched at once (no pagination)
